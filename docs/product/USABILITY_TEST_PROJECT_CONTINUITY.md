# 新手可用性测试：项目连续性

状态：ready  
日期：2026-08-18  
对象：桌游设计经验 0–1 个项目、已完成或准备完成一次原型改动的新手

## 研究目标

验证本地项目护照能否帮助新手：

1. 区分体验意图、当前问题、版本变化和下一步动作；
2. 把一次工具记录放回明确版本，而不是形成孤立表单；
3. 理解记录数不是进度分；
4. 在不知道 JSON 技术细节的情况下带走完整项目包；
5. 注意首版只支持一个项目和本地数据的备份边界。

本轮不判断参与者的项目管理能力，也不证明本地存储适合长期档案。

## 建议样本与主持边界

- 5 名中文新手；至少 3 名带来自己的真实项目描述；
- 不替参与者决定版本号、问题或下一步；
- 不先解释“版本节点”“本地优先”或“项目包”；记录他们如何理解；
- 首次停顿超过 20 秒才提醒继续说出想法；
- 不以任务最终完成掩盖第一次偏离。

## 任务

### P1：建立一个可行动的项目护照

场景：你的游戏让玩家经营一个港口网络。你希望玩家为了长期路线放弃眼前得分，但还没有证据。把这个状态记录到网站。

成功信号：参与者能分别填写体验意图、一个可回答的当前问题和一个包含具体动作的下一步；没有把三个字段写成同一句口号。

### P2：保存一次版本变化

场景：你把公开订单从 5 张减到 3 张，其他规则不变。准备测试这一版。

成功信号：版本、阶段、变化摘要和当前问题均可追溯；保存后页面显示一个版本节点。

### P3：让测试计划继承项目版本

场景：为刚才的版本记录一次测试计划，不重新输入项目名或版本。

成功信号：测试面板显示当前项目版本；问题默认来自项目护照；参与者能修改问题而不改变项目护照。

### P4：识别本地证据而不误读进度

场景：再保存一条反馈，然后回到首页说明两个数字表示什么。

成功信号：参与者说出它们是本站工具记录和版本节点，不把数量解释成完成度、质量或距离出版的百分比。

### P5：带走完整项目包

场景：你准备换电脑，请带走这个项目在本站的全部记录。

成功信号：参与者找到完整项目包导出；知道文件保存在自己的设备；能指出它不包含纸面原型、图片或外部规则文件。

### P6：发现单项目边界

场景：你还在设计另一款派对游戏。你准备如何处理？

成功信号：参与者注意到首版只维护一个活动项目，不直接把两款游戏的记录混入同一导出；会先导出当前项目并等待多项目支持或使用另一浏览器环境。

## 记录字段

- task_id、participant_id、device、viewport；
- start/end、完成/部分/失败；
- first_deviation、recovery、主持人提示次数；
- 对“当前问题”“下一步”“版本节点”“记录数”“完整项目包”的原话解释；
- 是否注意单项目与本地备份边界；
- 导出文件中缺少/多出什么；
- 严重度与修订假设；
- 修订后需要重测的任务。

## 进入下一轮的门槛

- P1–P5 每项至少 3 名新手无主持帮助完成；
- 没有人把记录数当作质量或完成度评分；
- 没有人误以为导出包含外部原型文件；
- 单项目边界在混入第二个项目之前被发现；
- 375px 下编辑、保存、测试和导出入口可操作且无页面级溢出。
