# 玩家人数配置契约：形成性可用性测试

对象：`special-player-count-configuration`  
更新：2026-08-19  
状态：planned；尚未招募参与者

## 本轮问题

新手能否不把“支持人数”误解为“体验完全相同”，并为一个已有三人原型写出可执行的 2/3/4 人配置差异？

## 参与者

- 3–4 名首次系统设计桌游的新手；
- 2 名有多人数测试经验的设计者或开发者；
- 至少 1 名经常在两人和四人以上组局的玩家；
- 尽可能包含一名需要额外读取、操作、沟通或时间支持的参与者。

这不是代表性样本，不用于估计成功率或玩家人数偏好。

## 任务

给参与者一个可运行的三人市场竞争原型摘要，以及“希望支持 2–5 人”的项目目标。不得先解释术语，让其：

1. 为 2、3、4 人写配置 ID 与主要/支持/实验层级；
2. 画出每个配置谁能直接影响谁；
3. 拆分自己回合、局外触发和公共阶段的总行动；
4. 选择一个市场或地图缩放项并写功能理由；
5. 为两人局决定是否用功能性 dummy，并逐动作写维护；
6. 判断四人局是否改成同时行动，并补齐锁定与冲突顺序；
7. 写一个能跨人数比较和一个不能直接比较的指标。

## 观察记录

- 第一次把人数当作单一倍率的位置；
- 是否主动区分人数、队伍、角色和模式；
- “互动拓扑”“局外触发”“功能性 dummy”“主要配置”的首次停顿；
- 是否为每个增减项写出功能，而非只填数量；
- 是否把 dummy 写成完整第三名玩家或单人 bot；
- 是否认为同时行动天然无冲突；
- 是否用 BGG 票数替代测试；
- 主持人首次解释、改写或代填的位置；
- 完成后的自述理解，不以表格填满作为成功。

## 形成性成功条件

- 参与者能说出“可运行”“实验”“支持”“主要”不是同一承诺；
- 至少一个缩放项包含明确功能和可观察失败信号；
- 低人数修补只承担已声明功能，并写出维护；
- 同步行动包含锁定、串行冲突或信息规则；
- 跨配置比较保留版本、座位、熟练度与含义边界。

若只有主持人不断解释后才能完成，不算通过；保留介入并改写指南。

## 禁止结论

- 不据此宣布指南易用、有效或普遍适用；
- 不计算统一完成率、缩放分或设计能力分；
- 不用参与者选择决定最佳人数；
- 不把熟练设计者的完成速度当新手阈值；
- 不把一次模拟任务当真实 2/3/4/5 人测试。

## 后续决策

若多数首次停顿集中在“拓扑”，先加入一张关系图示例；若集中在“总行动”，把自己回合/局外/公共/冲突表提前；若 dummy 仍被理解为完整对手，改用“功能替身”作为首显标签；若表格负担过重，先保留主要配置与一个边缘配置，不删证据边界。
