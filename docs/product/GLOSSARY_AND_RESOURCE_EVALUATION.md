# 概念词表与资源评价模型

状态：review  
日期：2026-08-20

## 为什么需要两套结构

词表解决“同一个词在不同指南里是否指同一件事”；资源评价解决“这条来源适合怎样读、能支持什么、哪里会误用”。两者都不负责替设计者打质量总分。

## 概念词条

规范词条保存在 `content/glossary.json`。每条包含：

- 稳定 `id`、中文规范词与别名；
- 一句新手定义；
- `notThis`：最常见的误读；
- 贯穿桌面例子；
- 适用阶段与引用它的指南；
- 相关词条；
- 资源与 Claim 外键；
- 审阅状态。

定义只在词表维护。指南使用 `conceptIds` 连接，不复制另一套规范定义。文章仍可用自然语言解释，但若含义变化，应先更新词条并记录原因。

## 资源评价不是排行榜

不同来源承担不同任务。论文可能适合界定模型却不适合直接给练习；设计日志能展示具体决定却不能估计普遍规律；玩家文章能暴露群体与操作问题，却不提供发生率；工具目录适合查找入口但时效风险高。

每条资源按以下维度记录，不相加：

| 维度 | 要回答的问题 |
|---|---|
| `useMode` | 适合学习、诊断、比较、查询还是案例研究？ |
| `reviewDepth` | 本项目读到全文、文章正文，还是只核验元数据/摘要？ |
| `contextClarity` | 作者、样本、项目和适用语境是否明确？ |
| `actionability` | 提供练习、步骤、诊断框架、具体案例还是目录？ |
| `transferability` | 可广泛迁移、需要条件，还是主要服务特定类型？ |
| `currencyRisk` | 内容是否容易因工具、平台、价格、行业流程而失效？ |
| `rightsStatus` | 可核验复用、只链接摘要，还是受限访问？ |
| `commercialContext` | 是否处在作者产品、出版物或平台的商业语境中？ |
| `bestFor` | 在什么设计问题上最值得打开？ |
| `doNotUseFor` | 最容易被误用来证明什么？ |

评价回答“怎样使用”，不是“谁更权威”。界面不得把这些字段压成星级、百分制、信任分或默认排序权重。

## 维护规则

1. 新资源先进入来源台账，再建立机器记录；
2. 没有正文级阅读时不得标 `full_text` 或 `article_level`；
3. `rightsStatus` 不明确时默认 `link_and_summarize`；
4. 高时效风险资源要显示核验日期；
5. 商业语境是透明信息，不自动降低质量；
6. 评价变化更新现有记录，不复制第二条；
7. 构建期校验所有资源恰好有一条评价，所有词条关系均可解析。

## 当前范围

- 146 个新手规范词条；最新增加空间模型、邻接规则、移动度量、节点度数、路径距离、空间瓶颈、空间密度、地点容量、模块地图布局、地图可读性与桌面区域，且都保留“不要把它当成”的边界；
- 六篇核心指南均将连接 `conceptIds`；
- 387 条资源各有一条无总分评价记录；
- 网站“方法”页提供理论框架、概念词表与“怎样读资源”三个入口；资源库使用同一审阅记录提供新手层级、使用方式筛选，并直接显示“最适合”和“不要用来”。十八条策展入口只缩小任务选择，不形成排名。
