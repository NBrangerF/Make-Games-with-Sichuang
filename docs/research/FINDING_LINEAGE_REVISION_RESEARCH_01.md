# 发现沿革与后继修订研究 01

日期：2026-08-21  
范围：桌游跨轮发现的只读重开、不可覆盖修订、审计轨迹与来源撤回  
状态：已用于 schema v2 与交互实现

## 研究问题

1. 一份已保存的发现后来需要改变时，怎样保留过去判断而不是覆盖？
2. 最小沿革需要哪些字段，才能解释“何时、为什么、改了什么”？
3. 桌游迭代日志怎样帮助新手理解修订不是线性升级？
4. 来源会话撤回后，后继修订应怎样处理？

## 检索与选择

本轮优先检索标准组织、可访问全文的方法论文、设计团队一手文章、设计师迭代日志与桌游设计日志。检索词围绕 provenance、revision、audit trail、iteration log、playtesting stages、designer diary 展开。只采用能够支持字段或交互决定的材料；没有把版本控制软件规则直接当作研究结论，也没有使用汇总页替代原始来源。

## 关键来源

### 1. W3C PROV-O

- 链接：https://www.w3.org/TR/prov-o/
- 类型：来源标准。
- 可迁移内容：`wasDerivedFrom` 可以形成来源链；`wasRevisionOf` 表示新实体保留原实体的大量内容；加入或删除描述会形成不同实体；修订与失效是不同关系。
- 产品含义：已完成发现不能原地变形。后继需要新 ID、父记录与沿革关系；撤回不是“写一个新版本就算了”。
- 边界：本站不是语义网系统，只实现最小的本地父子沿革。

### 2. White、Oelke 与 Friesen：大型质性资料的审计轨迹

- 链接：https://journals.sagepub.com/doi/10.1177/160940691201100305
- 类型：学术方法实践。
- 可迁移内容：分析结构和编码发生变化时，应在变化发生时记录；审计轨迹需要能说明何时、为什么以及改变了什么，演化中的分类结构也应保留理由。
- 产品含义：只有“修订 2”不够；后继保存前必须填写修订理由，同时保留新旧时间。
- 边界：健康质性研究的可信性程序不等于桌游发现得到认证。

### 3. Mark Rosewater：Playtesting（2026）

- 链接：https://magic.wizards.com/en/news/making-magic/playtesting
- 类型：大型卡牌游戏设计团队一手实践。
- 可迁移内容：游戏设计是提出、游玩、反馈、改变的迭代；测试方式随探索、愿景、成型和最终阶段改变，后期更快、更细；实际游玩不能被理论推演替代。
- 产品含义：后继修订应保留当时问题和来源版本，不能只显示累计次数；新修订也不自动代表成熟。
- 边界：Magic 的组织、卡池和资源不能成为独立桌游的测试次数门槛。

### 4. Timo Bron：Plateau of Leng Iteration Log

- 链接：https://timobron.com/document/document-plateau-of-leng-iteration-log/
- 类型：个人设计迭代日志。
- 可迁移内容：七个版本分别保留改动、截图和为何改变，并与测试日志配对。
- 产品含义：历史列表应能打开旧记录；创建后继时继承来源快照，再要求写新的修订理由。
- 边界：数字关卡案例只能迁移日志结构，不能作为桌游测试有效性的证明。

### 5. Kevin Wilson：Weirdwood Manor 设计日志

- 链接：https://boardgamegeek.com/blog/1/blogpost/159260/designer-diary-the-story-of-weirdwood-manor
- 类型：桌游设计师一手回顾。
- 可迁移内容：早期测试用于删减和简化；随后用表格追踪多个系统指标；更晚的测试转向合作、策略、能力使用与规则疑问等较难量化的问题。
- 产品含义：沿革需要保留每轮问题和适用边界，“最新”不能被设计成质量徽章。
- 边界：单款游戏的一百多场测试不是样本量或成熟度标准。

## 综合结论

### 已完成记录保持不可变

一旦记录进入历史并可能被引用，覆盖会破坏两条信息：当时设计师知道什么，以及后来的判断从哪里来。v2 因此把“查看”和“修改”分成两种动作：查看始终只读；修改只能创建后继。

### 最小修订字段

每份记录需要：

- `id`：本次修订自己的身份；
- `lineageId`：同一发现沿革；
- `revision`：沿革内递增编号；
- `parentRecordId`：实际从哪份旧判断创建；
- `revisionReason`：为什么此刻需要改变；
- `createdAt` / `completedAt`：何时创建草稿与何时固定记录。

旧记录从 v1 迁移时以自身 ID 作为沿革 ID、修订号设为 1，不猜测不存在的父子关系。

### “最新”不是“最好”

历史界面可以提示沿革存在更高修订号，但不能用绿色通过、成熟度或默认覆盖表达优越性。用户仍需阅读边界、反例、竞争解释和修订理由，也允许从旧修订创建分支。

### 撤回必须沿派生链传播

只删除直接引用撤回会话的记录还不够：若某个后继已经改用新的来源快照，它仍然从失效父记录派生。本站因此先找直接依赖，再沿 `parentRecordId` 反复寻找所有后继，并同时处理未完成后继草稿。外部导出不受本站控制。

## 没有推出的结论

- 没有证明 v2 让发现更正确或减少偏见。
- 没有把修订号当作证据强度、成熟度或发布状态。
- 没有自动选择“当前真相”、自动合并分支或自动解决冲突。
- 没有完整实现 PROV-O、团队权限、云同步或多项目协作。
- 没有完成真实新手、屏幕阅读器或跨浏览器可用性验证。
