# 玩家人数缩放、低人数 dummy 与配置差异：研究报告 01

更新：2026-08-19  
状态：review；外部证据综合与首轮产品化完成，中文参与者测试待办

## 研究结论

盒侧的“2–6 人”不是一个连续数值，而是若干需要分别说明、实现和测试的配置。人数变化至少可能改动五类东西：

1. **总量**：整局行动数、供给消耗、回合间触发、投票数和结束速度；
2. **拓扑**：直接对手数、第三方受益、联盟、邻接、队伍与信息路径；
3. **密度**：地图占用、市场竞争、候选信息、资源稀缺和可攻击目标；
4. **所有权**：一名玩家是否兼任多个角色、谁维护公共系统、谁拥有最后决定；
5. **交付成本**：等待、噪声、桌面空间、设置、组件、教学与规则分支。

因此“同一套规则能跑”不能证明体验承诺相同；“按人数乘除”也不能处理第三方、局外行动、投票和角色合并造成的结构变化。

## 一、人数改变的是配置，不只是倍率

Goodman、Perez-Liebana 与 Lucas 用 8 款已实现桌游、2/3/4 人配置和计算代理比较游戏空间。论文没有发现一个跨游戏一致的玩家人数效应，而是把游戏区分为“特征会随人数显著改变”和“没有显著改变”的两组。它测的是搜索代理和游戏树，不是人的乐趣，但足以反驳“所有游戏都按同一种缩放规律变化”。论文同时指出，两人零和游戏的部分理论性质不能简单延伸到三人以上；第三方合作与对手模型会改变决策环境。

Cole Wehrle 对 Root 的记录提供了桌面案例：规则不改也可以运行两人局，但三人以上的战斗会让未参战者受益，并形成某种生态回调；两人局更接近直接零和，早期击倒更容易。问题不是地图在物理上过大，而是地图生态过空。由此可见，人数配置应记录“谁能影响谁、谁从冲突获益、落后者怎样恢复”，不能只记录每人资源。

## 二、总行动量可能线性、乘法或近似指数变化

《Amritsar: The Golden Temple》的主要开发配置是三人。两人和四人测试暴露了神庙区域兴趣和完成速度问题，最终按人数调整空间数量。由于玩家能在别人回合跟随行动，三人到四人的建造机会并非简单增加一个人的份额；设计者将其描述为接近指数式变化。两人局则缺少局外触发，于是加入由大君移动触发的第三方工人，恢复“跟随”机会。

这类系统应至少分别计算：

- 每名玩家自己的回合和动作；
- 每个他人回合可触发的动作；
- 公共阶段、投票、刷新和结束检查；
- 同时行动中仍需串行解析的冲突；
- 因人数增加而新增的邻接、配对、目标或联盟关系。

只看“每人四行动”会漏掉局外行动和公共解析；只看实际局长又会把思考、教学、查询和规则分支混在一起。

## 三、缩放应绑定缺失功能

Games Precipice 的实践文章把地图区域、牌库和通用组件增减列为常见手段，也提醒某些游戏以特定人数为核心。具体规则说明了“为什么加东西”比“加多少”更重要：

- **Dixit 三人局**：每名非讲述者出两张而不是一张，使桌面仍有五张候选图像；修补的是谜题候选与干扰信息量，不是在模拟第四名玩家。
- **Amritsar 两人局**：第三方工人触发局外跟随；修补的是回合间互动机会，不需要完整分数、资源或策略。
- **Codenames 两/三人变体**：玩家在同一阵营对抗模拟对手，并以清除的敌方牌数形成结果；它改变了竞争结构和结果解释，不能被称为标准团队局的等价物。
- **Captain Sonar 低人数**：玩家合并 Captain、First Mate 和 Engineer 等角色，2/3 人不能使用实时模式；修补的是角色覆盖，但也改变了认知负担、沟通与时间结构。

本站因此采用“功能性 dummy”：只声明它维持的公共消耗、阻塞、触发、目标、信息噪声或时钟功能，并逐动作记录维护。它不自动代表第三名真人，也不等于正式单人自动对手。

## 四、等待的修补往往是结构重构

Victor Saumont 的 Popcorn 日志记录了发行方对四人等待的担忧。改为同时行动后，作者称局长接近减半，但这不是把“同时”写进规则就完成：依赖先后顺序的建造被移到轮间，口碑行动需要新增广告板来表达未来效果。同步化改变了时机、冲突解析、信息可见性和组件。

《In the Palm of Your Hand》的既有设计日志也记录了不参与当轮表演/猜测者的等待问题，团队结构因此重做。Captain Sonar 则显示反方向：多人时每人只承担一个实时角色，人数下降后角色合并，实时模式反而不可用。

所以高人数修补需回答：

- 玩家等待时是否仍能观察、预测、谈判或准备；
- 哪些动作可以真正同时，哪些必须锁定、排序或冲突解决；
- 同时行动是否泄露信息或让操作速度变成无意优势；
- 角色拆分是否增加沟通价值，角色合并是否压垮一名玩家；
- 新手、无障碍需求、主持劳动和桌面噪声是否随人数改变。

## 五、主要配置、边缘配置与人数范围

Daniel Piechnick 建议许多项目先用两人测试、把 2–4 人当常见范围，并用快速回合、团队或同时行动处理更高人数；他也以 Radlands 为反例，说明为出版吸引力增加 1–4 人模式反而偏离了作品的两人对抗核心。这些数字是个人专业工作流与市场判断，不是行业定律。

更稳健的做法是为每个项目声明：

- **主要配置**：最完整地承诺目标体验，也是开发资源优先投入处；
- **支持配置**：已完成规则、组件和目标玩家验证，但允许明确差异；
- **实验配置**：当前只证明可运行或用于诊断，不进入盒侧承诺；
- **不支持配置**：解释缺失的关键功能，而不是临时塞入一条未经测试的变体。

人数范围是产品承诺和生产决定，不应仅由“理论上能坐下”决定。

## 六、社区“最佳人数”只能做发现信号

BoardGameGeek XML API 暴露用户建议人数的 Best / Recommended / Not Recommended 票数与汇总。它能帮助发现值得复核的配置，但 API 字段不包含代表性抽样、玩家熟练度、实际局次、版本、团队结构、座位、教学方式或为何投票等语境。Daniel 的 Radlands 轶事也表明，一次非目标配置体验可能直接进入公开评分。

因此本站不把 BGG “best with”当作设计效果、市场比例或盒侧人数的自动裁决。使用时应：

1. 保留总票数和抓取日期；
2. 把它作为“优先观察哪个配置”的线索；
3. 回到具体长评、规则差异和真实桌面测试；
4. 不把少量投票、未玩过其他配置或旧版本票数合并成普遍结论。

## 七、人数配置契约

首轮最小记录如下：

- `configuration_id`：人数、团队、角色、模式和版本的唯一组合；
- `configuration_status`：主要 / 支持 / 实验 / 不支持；
- `player_count_promise`：此配置保留什么、不承诺什么；
- `fixed_elements` 与 `scaled_elements`：不变与变动项及其功能；
- `interaction_topology`：直接对手、邻接、第三方、联盟、信息与决定权；
- `total_action_model`：自己回合、局外触发、公共阶段、同时/串行解析；
- `market_or_map_density`：候选、占用、刷新、稀缺和结束速度；
- `role_merge_or_split`：角色归属、沟通与认知劳动；
- `dummy_function_and_upkeep`：保存的功能、操作、信息、平手和卡死；
- `seat_and_turn_order`：首末位、邻接、队伍和换座；
- `space_component_teaching_delta`：桌面、组件、设置、教学和协助；
- `configuration_specific_failure`：只在该配置出现的第一次故障；
- `cross_count_comparability`：哪些指标可以比较，哪些已是不同体验。

## 产品决定

1. 新增专题指南“把 2–5 人拆成可测试的人数配置”。
2. 新增人数配置、主要人数配置、互动拓扑、缩放维度、功能性 dummy、角色合并六个术语。
3. 新增独立资源入口，组合计算研究、设计师实践、官方规则和玩家症状。
4. 复用测试计划、测试方式选择、决定轨迹、共享决定观察和反馈分拣，不开发自动配平器。
5. 不生成统一缩放分、不根据 BGG 投票自动推荐人数、不承诺跨人数体验相同。

## 来源与证据边界

| 来源 | 证据任务 | 采用内容 | 不能推出 |
| --- | --- | --- | --- |
| Goodman et al., *Visualising Multiplayer Game Spaces* | 计算研究 | 不同游戏随人数变化的特征并不一致；两人与三人以上对手模型不同 | 人类乐趣、最佳人数或通用缩放公式 |
| Daniel Piechnick, *Player Count* | 设计师实践 | 人数范围、测试可达性、制造与 Radlands 反例 | 2–4 的行业定律或市场比例 |
| Games Precipice, *Player Count & Scalability* | 实践综述 | 地图、牌库、组件与核心人数的候选缩放 | 任一手段的效果证明 |
| David Heras Pino, *Amritsar* diary | 一手日志 | 局外行动总量、区域空间与功能性第三方工人 | 具体空间数或“指数”适用于其他系统 |
| Cole Wehrle, Root Hirelings diary | 一手日志 | 两人零和化、地图生态、跨人数失败与重构 | 所有三人局都能自平衡 |
| Victor Saumont, Popcorn diary | 一手日志 | 同时行动牵连时机、组件与局长 | 同时行动普遍减半时间 |
| Dixit / Codenames / Captain Sonar 规则 | 官方规则 | 候选信息、模拟对手、角色合并和模式切换 | 玩家偏好或设计过程 |
| BGG XML API2 | 平台数据结构 | 用户建议人数票数是社区信号 | 代表性样本、原因或效果 |
| In the Palm of Your Hand diary / 中文玩家长评 | 一手与玩家症状 | 等待、参与角色和停机时间候选 | 总体发生率或修订成功 |

多数一手日志来自已发行商业产品，失败项目和中文设计过程仍不足。学术证据依赖计算代理，不测人的社交、身体和教学经验。官方规则只能证明发布时如何配置，不证明体验等价。本站综合出的契约尚未经过中文新手、不同无障碍需求、不同桌面空间和混合熟练度群体测试。
