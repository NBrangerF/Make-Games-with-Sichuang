# 议题到系统：把社会、文化与教育主张变成可测试的桌游关系

状态：research-complete / product-validation-pending  
更新：2026-08-21

## 研究问题

1. 什么使一个议题成为玩家能在行动中遇见的系统，而不只是贴在机制上的文字？
2. 价值怎样被翻译成角色、权限、资源、约束与反馈？
3. 抽象化删掉了什么，遗漏怎样改变责任、能动性和因果解释？
4. 谁的证据可以支持“表达成立”，谁应有质疑和修改权？
5. 复盘能做什么，又不能替系统承担什么？

## 方法与证据层级

本轮以两套本地课程为情境样本，深读 8 个公开来源：1 篇方法论文、1 篇方法工具案例、2 篇教育/公民设计案例、1 组设计正义原则、1 篇社会改变游戏实践论文、1 篇算法素养桌游案例和 1 篇桌游抽象批评。检索还查看了相关书目与二级入口，但未把只看摘要或不直接回答问题的页面写进权威资源表。

这不是系统综述，也没有覆盖所有语言、地区和议题类型。单个课堂或项目只能提供设计模式、失败症状与待测假设，不能证明学习、态度或行为改变。

## 综合结论

### 1. 先写“系统主张”，再选机制

系统主张是一句可被原型反驳的关系陈述，例如“平台把可见度奖励给持续制造互动的人，同时把审核成本转移给创作者”。它比“让玩家了解网红经济”更可测试：设计者可以追踪哪些动作改变可见度、成本由谁承担、反馈何时出现。

### 2. 用六字段完成价值翻译

把系统主张拆成：角色、权限、资源、约束、反馈和时间尺度。每一字段都要落到玩家动作、可见信息或系统响应。主题名词、知识题和结论卡可以辅助语境，但不能代替核心关系。

### 3. 抽象必须附带遗漏账本

每次简化都记录：删掉了谁或什么因果、为什么当前原型需要删、可能形成什么误读、谁能发现它、何时补查。遗漏账本不是要求模拟现实全部细节，而是让设计者看见“可玩性选择”同时也是表达选择。

### 4. 验证需要三层证据

- 系统行为：原型是否真的产生预期的资源流、权限差异和反馈；
- 玩家解释：玩家怎样描述因果、责任与替代策略；
- 受影响者审阅：直接了解或承受议题的人怎样评价遗漏、位置和伤害。

三层证据不能互相代替。玩家能赢不等于理解，能复述设计者结论也不等于系统表达成立，单次利益相关者审阅也不等于代表一个群体。

### 5. 复盘有边界

复盘适合比较“游戏中发生了什么”“玩家怎样解释”“现实还缺什么”，也适合揭示替代模型。若核心因果只在主持人讲解时出现，系统仍然断裂。下一版应先修改行动、权限或反馈，再决定复盘需要保留多少。

## 形成的可追溯 Claim

- `claim-issue-needs-system-thesis`：复杂议题需要可反驳的系统关系，不只需要主题目标。
- `claim-abstraction-needs-omission-ledger`：抽象化应记录删去内容及其解释风险。
- `claim-values-verification-needs-layered-evidence`：系统、玩家解释和受影响者审阅必须分层。
- `claim-debrief-cannot-repair-system-disconnection`：复盘不能替断裂的行动—反馈关系补讲结论。

## 产品决定

网站增加“别把观点贴在棋盘上，先让玩家在系统里碰到它”专题指南，不新增总分、议题正确答案生成器或社会影响评分。新手完成五步后进入现有原型、决定轨迹、测试与反馈工具；任何公开案例仍要单独完成权利、隐私和利益相关者复核。
